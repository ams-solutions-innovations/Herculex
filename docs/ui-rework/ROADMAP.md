# Herculex UI/UX Rework — Roadmap

Status: **Phase 9 in progress 2026-08-15** (676 tests green, +4 skipped, 0 analyzer errors). Profile's own screens are migrated off `AppColors`; the shim itself, the `ValueKey` rebuild hack, and the app-wide literal-color sweep are NOT done (see Phase 9 outcome — ~98 files / ~1,416 references still call `AppColors.*`, all outside `lib/features/profile/`). Phase 7 (Workout) is still blocked on GSD Phase 10 landing.

Full plan with per-phase tasks, risks, and verification lives in the approved implementation plan; this file tracks the phase ledger and decisions. Do not fold this into `.planning/ROADMAP.md` — GSD Phase 10 (assisted reps) is in flight and `lib/features/reps/` is off-limits to this track.

## Decisions (user-approved 2026-08-14)

1. **Foundation-first** phasing: quick wins → tokens/theme/font/light-mode → component library → navigation → tab-by-tab migration with feature work embedded.
2. **One global bottom nav + central "+"** opening an animated quick-add popup. Contextual navigation inside sections goes on top (segments/tabs). No per-section bottom bars.
3. **Bold new visual identity**: bundled font (Manrope body + Space Grotesk display proposed), domain color-coding (nutrition/training/fasting/recovery), distinctive shapes/gradients. Prototyped on the Dashboard first; user approves before systemizing.
4. **Fasting auto-schedule is in scope** (own phase).
5. **4 tabs + "+"**: Dashboard · Nutrition · [+] · Workouts · Profile. Programs folds into Workouts as a top segment (Sessions | Templates | Programs).

## Phase 1 outcome (for the checkpoint review)

**Type.** Manrope (body/UI) + Space Grotesk (headlines and stat numerals), both SIL OFL, bundled as variable fonts in `assets/fonts/` with their licenses. A probe confirmed Flutter maps `fontWeight` onto the `wght` axis, so one file per family covers the full range (Manrope 200–800, Space Grotesk 300–700). Tabular figures are on for display, headline and `titleLarge`, so stat columns and running timers stop jittering.

**A latent bug this uncovered:** `ThemeData.fontFamily` does not reach a `textTheme` passed through `copyWith`, so the app had been rendering in the platform default all along — bundling `Inter` alone would not have changed anything. Every style now names its family explicitly.

**Color.** `HxColors` (`lib/theme/tokens/hx_colors.dart`) is the single source of truth: two const palettes registered as a `ThemeExtension` and read as `context.hx`. `AppColors` is now a thin shim over it, so the ~1,500 legacy call sites keep working unchanged while tabs migrate. Light mode gained a real surface ladder — page `#E4EFFC`, cards `#F5F9FF`, sheets `#FFFFFF` — which is what fixes cards vanishing inside sheets. `primaryText` is the darkened variant for text (light `#0063CC` clears 4.5:1; the vivid `#0A84FF` stays for fills). Domain accents: training blue, nutrition green, fasting teal, recovery violet.

**Startup.** Brightness now resolves in `main()` from the saved mode plus the platform value before the first frame, so a light-mode device no longer flashes dark surfaces. `theme_provider` no longer assumes `system` means dark.

**Prototype.** The Dashboard header is left-aligned with a time-of-day greeting over the name in Space Grotesk, and the fasting card is fully teal (ring, labels, both CTAs) to demonstrate domain color-coding.

**Deferred to later phases as planned:** the migration-enforcement script (P2 onward, once `lib/ui/` exists), removing the `ValueKey` rebuild hack in `app.dart` and deleting the shim (P9).

## Phase 2 outcome

`lib/ui/` now holds the shared primitives, exported through `lib/ui/ui.dart`.

**`HxGlass`** is the frosted-glass base: backdrop blur, translucent themed fill, hairline border — and deliberately no colored shadow or bloom, which is the standing rule for every glass surface including the Phase 3 nav bar. `GlassContainer` (11 adopters) is now a thin adapter over it, so its hardcoded hex fallbacks that never matched light mode are gone.

**`HxScreenShell`** is the centerpiece: a frosted back button and title pill float over the content, hide when you scroll down and return the moment you scroll up. A 12px directional threshold stops ballistic jitter from flickering it, the header is forced visible near the top so short pages can never strand it, and an optional `pinnedBottom` slot keeps a primary action always reachable (Phase 5's Start Fast depends on this). Seven widget tests in `test/widgets/hx_screen_shell_test.dart` pin the behavior.

**`HxCard`, `HxPill`/`HxTextPill`, `HxStatTile`** are promoted from the private helpers that were trapped inside the 2,400-line `dashboard_widgets.dart`. `HxCard` takes an optional `accent` for domain color-coding; the dashboard's `_card()` and its four macro cards now delegate to them, deleting ~70 lines of bespoke layout.

**`HxSheet`** succeeds `app_bottom_sheet.dart` with token surfaces and a `pinnedBottom` slot; **`HxTopTabs`** is the in-section segmented control Phase 3 needs for Programs-inside-Workouts.

`weekly_calories_view.dart` is the first full adopter of the shell and now also reports intake against target.

## Phase 3 outcome

**IA:** `MainScaffold` now hosts 4 tabs — Dashboard · Nutrition · Workouts · Profile. Programs moved out of the bottom bar into a `HxTopTabs` segment (Sessions | Templates | Programs) inside `WorkoutsView`'s idle landing, switched via an `IndexedStack` so each segment keeps its scroll/filter state. `mainTabIndexProvider` indices were unchanged for Dashboard/Nutrition/Workouts (0/1/2); only Profile moved from 4 to 3, and no code jumped to the old Programs index (3) or old Profile index (4), so the reindex needed zero call-site fixes beyond the tab list itself.

**Known trade-off, deliberately deferred:** while a workout session is active, `WorkoutsView` shows `ActiveWorkoutView` full-screen and the segmented control (hence Programs) is not reachable — this exactly matches how Templates already behaved before this phase, so it's not a new regression, just Programs now inheriting it. Revisit if Phase 7 reshapes the active-session header.

**`HxNavBar`** (`lib/ui/hx_nav_bar.dart`) replaces the deleted `floating_nav_bar.dart`: frosted pill shell, sliding-position mechanics, and per the checkpoint feedback the selected bubble is a flat filled circle with **no colored shadow and no halo pulse**. **Follow-up feedback after first review**: the "+" moved out of the pill entirely — it is now a separate circular glass button riding outside the main bar on the right, in its own `quickAdd` accent color (a warm amber, new token in `HxColors`) distinct from both the neutral bar glass and the primary selection fill, so it never reads as a fifth destination. It rotates 45° via `AnimatedRotation` while the quick-add menu is open.

**`QuickAddMenu`** (`lib/features/shell/quick_add_menu.dart`): implemented as a `Positioned` overlay inside `MainScaffold`'s existing `Stack` rather than `OverlayPortal` — same visual result (backdrop + floating items above the nav bar), less machinery to keep in sync with the scaffold's own state. Five context-aware actions, each domain-tinted: Log food, Scan barcode, Log weight, Quick workout, and Start Quick Fast ↔ End Fast depending on `activeFastingSessionProvider`. Items reveal staggered outward from the "+" (closest item first) with a fade + scale + slide-up driven by one `AnimationController`; reversing it before `onClose` fires makes the close feel symmetric with the open.

Three flows were extracted from private, single-use methods into shared functions so both the dashboard cards and the quick-add menu call the same code: `quickLogWeight` (`features/measurements/presentation/quick_log_weight.dart`), `scanAndLogFood` (`features/nutrition/presentation/quick_scan_food.dart`), reusing the already-shared `confirmEndFast` from Phase 0. `app_shortcuts_service.dart`'s hardcoded Slovenian shortcut labels are now English, matching the rest of the app.

**Not yet a real "quick fast":** `startSession` takes a required `targetSeconds`, so Quick Fast currently starts a 24h ceiling session rather than a truly open-ended one (`kQuickFastTargetSeconds` in `quick_add_menu.dart`, called out for Phase 5 to replace with a nullable-target repository change).

11 new widget tests (`test/widgets/hx_nav_bar_test.dart`, replacing the deleted `floating_nav_bar_test.dart`). 628 tests green, 0 analyzer errors.

## Phase 4 outcome

**God-file split.** `dashboard_widgets.dart` (2,099 lines going in) is now a barrel (`export 'widgets/xxx.dart'`) over 14 files under `presentation/widgets/`, one per `DashboardWidgetType` (plus a `dashboard_shared.dart` for the promoted `dashboardCard`/`DashboardPill`/`dashboardTitle` helpers). Done as a scripted line-range extraction with automatic import-path adjustment, not manual retyping — verified byte-exact by `flutter analyze` (zero new errors) and the full test suite staying at the same pass count before/after. `dashboard_view.dart` needed no changes; it still does `import 'dashboard_widgets.dart'`.

**Charts off the dashboard.** The two real inline charts — `LiveMacrosGrid`'s trend graph (with its macro-chip + range-dropdown controls) and `BodyweightMiniCard`'s sparkline — are gone from the grid/card widgets themselves. In their place: `TrendCardsRow` (new `DashboardWidgetType.trends`, `widgets/trend_cards.dart`), a swipeable `PageView` of two read-only preview cards (kcal 7-day, bodyweight all-history) with a dot indicator; tapping either opens the real interactive chart — `/nutrition/weekly-stats` or `/measurements/bodyweight` (both already existed). `BodyweightMiniCard` also gained its own tap-through to the same route. `LiveMacrosGrid` dropped from `ConsumerStatefulWidget` to `ConsumerWidget` — no more local chart-selection state to carry.

**Per-macro dashboard customization.** New `MacroCardConfig`/`DashboardMacro` domain type (`domain/macro_card_config.dart`) mirrors `DashboardConfig`'s encode/decode/toggle/reorder shape exactly, scoped to the 4 macros `DailyTotals` actually tracks (confirmed no vegetable/fruit tracking exists, so that part of the original request is out of scope until such data exists). `macroCardPrefsProvider` persists it (`dashboard_macro_cards_v1` in SharedPreferences). `DashboardCustomizeSheet` gained a nested "MACRO TILES" `ReorderableListView`, shown only while the parent "Nutrition Overview" widget is itself visible. 6 new domain tests in `test/macro_card_config_test.dart`, mirroring `phase6_dashboard_test.dart`'s coverage style.

**Weekly-calories page enrichment.** Added a stats card: days logged in the selected range, plus (when a target exists) the day closest to and furthest from it — computed client-side from the same in-memory 92-day history, no new queries.

**Food-entry pills.** `_EntryTile` in `nutrition_view.dart` was a borderless `ListTile`; it's now a rounded pill card (border, spacing, bold kcal trailing) matching the app's card language, while keeping the same swipe-to-delete and tap-to-detail behavior.

**Deliberately descoped: Nutrition-tab-wide `HxScreenShell`/`HxSheet` migration.** `nutrition_view.dart` is 1,351 lines with a `PageView`-of-days architecture and a hand-rolled date-navigator header (prev/next arrows, date picker, overflow menu) — structurally a poor fit for `HxScreenShell`, which was built for pushed pages with a static title and a back button, not a root tab with interactive header controls. A full migration would also mean touching ~15 associated bottom sheets. Given the size and risk of a half-finished rewrite of a core tab, this phase shipped the bounded, high-value piece (food pills) and left the broader sheet-by-sheet conversion and `AppColors`→`context.hx` sweep for a dedicated future pass — the token sweep in particular has zero visible effect today (the shim is byte-identical to the tokens) so it's pure enforcement bookkeeping, not user-facing work.

## Phase 5 outcome

**Page, not sheet.** `fasting_bottom_sheet.dart` (1,129 lines) is deleted. `/fasting` (new route) renders `FastingView` on `HxScreenShell`, split into 4 files under `presentation/widgets/`: `active_fast_panel.dart`, `start_fast_panel.dart`, `fasting_insights.dart`, `fasting_history.dart`. All three call sites that used to open the sheet (`dashboard_view.dart`, both the active-session card and the idle card's outer tap and inner "START FASTING" pill) now `context.push('/fasting')`. Every `dynamic`/`as` cast onto session objects is gone — panels take a typed `FastingSessionData`.

**Quick Fast, without a schema migration.** `FastingRepository.startSession` still requires a concrete `targetSeconds` int, so a true nullable target was out of scope for this phase (tracked as a note for whenever Phase 6 next touches this table for auto-schedule). Instead, `FastingPlan.quickFast` carries a documented sentinel — `kQuickFastSentinelSeconds = 200h`, deliberately unreachable through the custom-hours slider (capped at 168h) — and `isQuickFastTarget()` detects it everywhere a session is rendered: `ActiveFastPanel`, the dashboard's active-fast card, and the quick-add menu's Start/End Fast action (which also stopped scheduling a goal notification for a fast with no goal). Quick Fast is the first tile in `StartFastPanel`'s list, rendering elapsed-time-only when active — no ring, no "remaining," a "TARGET: None" detail card instead of "TARGET END." 3 new tests in `test/fasting_plan_test.dart` pin the sentinel invariant.

**Pinned Start Fast.** `HxScreenShell.pinnedBottom` now holds the real "START FAST NOW" button when idle — genuinely fixed on screen, not just "near the top of a scrollable list" as the Phase 0 version had it. End Fast stays where it already read well: directly under the ring in `ActiveFastPanel`, the first thing on screen with zero scrolling — not duplicated into the pinned slot, since it's already always reachable from there, the dashboard card, and the quick-add menu.

**Three ways to delete a session.** Swipe-to-delete and the detail-sheet's delete button already existed; long-press now arms a row (its status icon flips to a red X) and a second tap deletes — mirroring the exact interaction pattern `workouts_view.dart`'s `_RecentTab` already uses elsewhere in the app, not a new one. All three paths funnel through one shared confirm dialog in `fasting_history.dart`.

**Identity.** A large low-opacity `Icons.watch_later_rounded` sits behind the page content in `domainFasting` teal — the clock motif from the original brief. Timer numerals already render in Space Grotesk for free, since that's the display font `AppTheme` wired up in Phase 1.

## Phase 6 outcome

**Schema.** `FastingSchedules` (v27, synced — `SyncColumns` + `SyncTombstone`): `planName` (a `FastingPlan` enum name), nullable `customTargetSeconds` (only used when `planName == 'custom'`), `daysOfWeek` (bitmask, bit `weekday - 1` per `DateTime.weekday`), `startTimeMinutes`, `enabled`, `autoStart`. Registered in `sync_table_specs.dart`/`sync_backfill.dart` and mirrored in `supabase/migrations/0009_fasting_schedules.sql` (RLS + triggers + realtime, spelled out directly rather than folded into 0003-0005's original loops, which already ran). `test/schema_v27_test.dart` + a new `migration_test.dart` fixture replay cover the migration; 667 tests green overall.

**A real bug this surfaced: `tz.local` was never set.** `FastingNotificationScheduler` (and `calendar_service.dart`) had called `tz.TZDateTime.from`/`tz.local` since it was written, but nothing in the app ever called `tz.setLocalLocation` — so `tz.local` silently defaulted to UTC, and every existing scheduled notification (including the pre-existing fasting-goal-reached one) fired at the wrong wall-clock time for any device outside UTC. Fixed in `main.dart` via the new `flutter_timezone` dependency, resolved before `runApp` alongside the existing `tz.initializeTimeZones()` call. This was a latent, ship-blocking correctness issue for the very feature this phase adds — a recurring reminder at a *specific local time* — so fixing it was in scope, not a drive-by.

**Scheduling.** `FastingScheduleService` (`features/fasting/data/`) issues one `zonedSchedule` per enabled weekday per row, using `matchDateTimeComponents: DateTimeComponents.dayOfWeekAndTime` so the platform itself re-derives the next matching instant week over week, DST included, once `tz.local` is correct. Notification ids are `2100 + scheduleId * 10 + (weekday - 1)` — the id block the original plan reserved (goal-reached notifications own 2001). Every edit does a full cancel-then-reschedule for that row (`rescheduleOne`); app launch does it for every row (`rescheduleAll` in `app.dart`'s `initState`), which also re-arms anything an Android reboot cleared.

**Honest scope on `autoStart`: no silent background start.** Neither platform runs Dart when a scheduled notification is merely *delivered* while the app isn't running — only when it's tapped — so true unattended auto-start isn't achievable without a native background-execution dependency this app doesn't carry (flagged as a real constraint in the original plan, not discovered late). `autoStart` instead means: tapping the notification starts the fast immediately (skipping if one is already active, never ending an in-progress fast out from under the user) instead of just opening the Fasting page for review. A tap while the app isn't running has no Flutter engine to act on, so it's queued (`PendingFastingScheduleActionQueue`, mirroring the existing `PendingWorkoutNotificationActionQueue` pattern exactly) and drained on next launch. The dispatch plumbing lives in `workout_notification_service.dart` (the one place `FlutterLocalNotificationsPlugin.initialize()` is ever called — the plugin's platform channel is process-global, so every feature's notifications route through its single response handler); a fasting-schedule tap is identified by payload prefix (`fasting_schedule:<id>`), checked before the existing action-id branch.

**UI.** `/fasting/schedule` (`FastingScheduleView`, reached via a new alarm-icon action on `FastingView`'s `HxScreenShell` header) lists schedules as swipe-to-delete cards (time · days · plan · next-occurrence preview · enable switch), with a pinned "Add Schedule" CTA. `FastingScheduleEditorSheet` (`HxSheet`) handles both add and edit: day-of-week circle toggles (always keeps at least one day selected, so there's no invalid-state to validate against), a time picker, plan chips (every `FastingPlan` except Quick Fast, which has no real target and makes no sense as a reminder's plan), the custom-hours slider reused verbatim from `StartFastPanel`, the autoStart/enabled switches, and a live "next 3 reminders" preview computed from the same pure occurrence math the scheduler itself uses.

**Pure, dependency-free core.** `fasting_schedule_occurrence.dart` (bitmask helpers, `nextOccurrence`/`nextOccurrences`, display formatting, plan resolution) has no Drift/notification imports, so the date math that both the editor's preview and the actual scheduler depend on is unit-tested directly rather than only indirectly through integration tests — 18 tests in `test/fasting_schedule_occurrence_test.dart`, including a year-boundary case. `fasting_schedule_payload_test.dart` (3 tests) and `fasting_schedule_repository_test.dart` (7 tests) cover the rest of the new surface.

## Phase 8 outcome

**Schema.** `v28` adds one nullable `IntColumn startTimeMinutes` to both `ProgramDays` (the day's default, copied onto each new occurrence at materialization time — same "default now, freely editable per occurrence" relationship `templateId` already has) and `ScheduledWorkouts` (the actual per-occurrence time). Both are plain nullable ints with no default and no `REFERENCES` clause, so the migration is two ordinary `ALTER TABLE ADD COLUMN`s — no `legacy_alter_table` rebuild — and per RB-04's sync design, no `sync_table_specs.dart` change either: `SyncService` derives the remote push/pull payload generically from whatever local columns exist beyond the registered FK/localOnly/dateTime sets, so `supabase/migrations/0010_schedule_start_time.sql` is a bare two-column `ALTER TABLE` on both remote tables and nothing else.

**A real migration bug this surfaced, worth remembering for any future addColumn-based block.** The v28 `onUpgrade` block initially crashed several schema-verifier tests (`fk_repair_test.dart`, `schema_v25/26/27_test.dart`) with `duplicate column name`. Two distinct problems, both now fixed: (1) unlike `createTable` (which drift always compiles as `CREATE TABLE IF NOT EXISTS`), `addColumn` has no such guard, and several migration tests build a fresh, current-schema database via `onCreate` and then rewind its stamped `user_version` to simulate an old install — so by the time `onUpgrade` runs, the column can already exist. Fixed by wrapping both `addColumn` calls in the same `tryAddColumn` try/catch idiom the v24 and v25 blocks already use. (2) Separately, and specific to this function: every `if (from < N)` block in `onUpgrade` gates only on `from`, never on `to`. `SchemaVerifier.migrateAndValidate` fakes an intermediate target version (e.g. 25) to test one migration step in isolation, so a v25/26/27-targeted test still had `from < 28` evaluate true and ran the v28 block anyway — silently adding `start_time_minutes` onto `program_days`/`scheduled_workouts` (tables that already exist at every one of those versions) and then failing schema validation against that older version's frozen reference schema with an "unexpected additional column". `createTable`-based blocks never hit this because an early table creation against a schema that doesn't track that table yet is an invisible no-op; `addColumn` mutates a table the reference schema already knows about. Fixed by gating the v28 block on `if (from < 28 && to >= 28)` — the only block in the function that checks `to`, deliberately scoped to just this block rather than refactoring the other 25 blocks, since none of them have ever touched a column on an already-tracked table from a future version before now.

**Domain + repository.** `scheduled_workout_row.dart` gained `startTimeMinutes`/`hasStartTime`/`startTimeLabel` getters plus a top-level `sortedByStartTime()` helper (chronological-first, `orderIndex` tiebreak, untimed sessions last — the ordering every timed UI surface below uses). `programs_repository.dart` gained `setProgramDayStartTime` and `setScheduleStartTime`; `createProgramFromSplit` gained `defaultStartTimeMinutes`; `materializeProgram` copies the day's default onto each newly materialized row.

**UI.** `block_builder_view.dart`'s step 4 gained a default-start-time picker per day. `day_detail_sheet.dart` gained a per-occurrence time editor and — per the original plan's ask — was converted from `AppBottomSheet` to `HxSheet` in the same pass (one leftover `AppBottomSheet` reference in its template-scope picker sheet was missed in the initial pass and caught during this session's verification via `flutter analyze`, then fixed). `session_tile.dart` now shows the time; `month_calendar.dart`'s day list sorts chronologically via `sortedByStartTime()`.

**A deliberate, documented UX trade-off in `day_column_card.dart` (week board).** Once any session on a day has an explicit start time, that day's list becomes read-only and time-sorted instead of the normal drag-to-reorder `ReorderableListView` — resorting a list that a `ReorderableListView`'s `oldIndex`/`newIndex` assumes is `orderIndex`-ordered would silently corrupt reordering otherwise. Days with no timed sessions are completely unchanged, still fully drag-reorderable. Worth re-reading this note before touching that file again.

**Deliberately descoped, mirroring Phase 4's precedent.** The optional reminder notification for session start times, and a full Programs-wide `HxScreenShell`/`context.hx` sweep beyond `day_detail_sheet.dart`. Also verified rather than re-fixed: the original plan's "white-on-white" bug reports at `month_calendar.dart:279` and `training_blocks_view.dart:223` were already fixed as a side effect of Phase 1's light-mode surface-ladder token work — current color values were checked directly, contrast is fine, no action was needed.

**Verification.** 676 tests green (+4 skipped, unchanged from before this phase), 0 analyzer errors. 7 new tests: 6 in a new "Session start times (Phase 8)" group in `test/phase4_programs_test.dart`, 1 in `test/schema_v28_test.dart`.

## Phase 9 progress (not yet code-complete)

**What's done.** The three Profile presentation files — `profile_view.dart` (1,642 lines), `custom_foods_view.dart`, `custom_recipes_view.dart` — are fully off `AppColors.*` and onto `context.hx.*` (89 call sites migrated, mechanical 1:1 since the shim's getter names already match `HxColors`' field names). The two sheets Profile still hand-rolled instead of using the shared shell — `_IdentitySheet` (the avatar-tap name editor) and `_AuthSheet` (Supabase sign-in/register) — are now built on `HxSheet` instead of a raw `Container` + manual grab-handle + `SingleChildScrollView`. Both needed an explicit `padding` override (`bottom: HxSpace.x5 + MediaQuery.viewInsetsOf(context).bottom`) to preserve the keyboard-avoidance the original hand-rolled version had — `HxSheet`'s default padding doesn't account for `viewInsets`, so a naive conversion would have covered the text field with the keyboard on smaller screens.

**Why the rest isn't done, and why that's a deliberate stop rather than an oversight.** The plan frames Phase 9 as the phase that finally deletes the `AppColors` shim entirely, once an enforcement script reports zero references. That's not achievable safely in one pass: **~98 files / ~1,416 call sites** outside `lib/features/profile/` still read colors through the static `AppColors.brightness` global (Dashboard, Nutrition, Workouts, Programs, shared widgets) — down from ~101 files / ~1,509 before this session's Profile work, which gives a sense of scale: Profile was 3 files and ~90 references, a small fraction of the total. Deleting the shim requires *every* one of those call sites migrated first, since any straggler would crash on `AppColors` no longer existing. The `ValueKey` rebuild hack in `app.dart` exists specifically because the static `brightness` flag doesn't propagate through `Theme` the way `context.hx` does — removing it before the shim is fully retired would silently break theme-switching for every still-`AppColors`-reading screen. Also skipped: the app-wide `Colors.white/black` (~129) and `Color(0x…)` (~110) literal sweep — spot-checking during this pass showed most of these are legitimate, theme-agnostic contrast colors (e.g. white text/icons on a colored filled button or pill, consistent everywhere in the app), not the light/dark surface bugs the original audit was chasing; a real sweep needs case-by-case judgment, not a mechanical pass, and was out of scope for this session.

**What this means for continuing Phase 9.** The remaining work is genuinely the bulk of the phase: migrating Dashboard/Nutrition/Workouts/Programs' remaining `AppColors` call sites (or accepting some as permanently out of scope, the way Phase 4 and Phase 7's plan already flag some sheets as deliberately unmigrated), re-counting to confirm zero references, deleting the shim, removing the `ValueKey` hack, and only then doing a real light/dark regression pass to confirm `ThemeExtension.lerp` alone drives every remaining screen correctly. Until that's done, Phase 9 stays "in progress," not "code-complete."
