<tasks>

1. Make the native renderer the sole owner of notification id `1` on API 36+. In `WorkoutNotificationService.showOrUpdate`, skip the `flutter_local_notifications` `_post()` call when the platform reports `android16Plus`, while still invoking `afterPost` so the native surface is published. Read the capability once and cache it rather than querying the channel on every tick. Below API 36 the Flutter path stays the only publisher and `afterPost` still runs.

2. Change the `Timer.periodic` in `showOrUpdate` from `Duration(seconds: 1)` to `Duration(seconds: 5)`. Elapsed time is drawn by the notification chronometer (`setWhen` + `setUsesChronometer`), so a 1 Hz repost buys nothing and Android rate-limits it.

3. In `OngoingWorkoutSurfaceAdapter.update`, compare the incoming parsed snapshot against the cached one and skip `renderer.show()` when they are equal apart from `collapsed.elapsedLabel`. Still call `stateStore.recordSurface` and still rebuild the action `PendingIntent`s only when the snapshot's `sessionId` or `targetSetId` changed. Log `event=updateSkipped reason=unchanged` so the device test can see the reduction.

4. Give the rest timer its own channel. Add `_restChannelId = 'workout_rest'` with a high-importance channel in `workout_notification_service.dart` and point `scheduleRestTimer` at it. Today it requests `Importance.max` on `workout_live`, which the system created at `IMPORTANCE_LOW`, so the alert is silently downgraded.

5. Call `OngoingWorkoutSurfaceBridge.instance.clear()` from `dispose()` in `lib/app/app.dart` alongside the existing notification cancel and drain-timer cancel. Today the native surface can outlive the widget.

6. Enforce `requiresUnlock` in `OngoingWorkoutActionReceiver`. Read the flag for the incoming action from the persisted surface state; when it is true, launch the app through the existing `MainActivity` intent instead of queueing the command, and log `event=rejected reason=requires_unlock`. No action is flagged today, so this is a guard against a future high-risk action being executed silently from the lock screen — it must not change behaviour for the five current low-risk action IDs.

7. Render the two already-populated but hidden diagnostics fields in the settings sheet: `lastRejectedNativeActionId` and the rejection reason. Place them next to the existing `Rejected Native` count so the stale-action and requires-unlock paths are visible during a device test.

8. Correct two false claims in the docs. In `docs/now-bar-native-adapter-contract.md` (the "Android API Gating" fallback bullet, ~lines 266-280), replace the statement that the `flutter_local_notifications` ongoing path is always kept with the actual rule: native owns the surface on API 36+, Flutter owns it below. In `docs/now-bar-workout-proposal.md` (~lines 232-236), replace "reflectively requests promoted ongoing behavior" with a description of the real `requestPromotedOngoing` / `ProgressStyle` / `setShortCriticalText` calls, and update the Samsung verification checklist so the expected `Style` reads `ProgressStyle`.

</tasks>

<success_criteria>

- Exactly one publisher writes notification id `1` per device tier: native on API 36+, `flutter_local_notifications` below 36.

- The rest timer alerts audibly on its own `workout_rest` channel.
- Backgrounding, ending a workout, and disposing the app widget all leave no ongoing workout notification behind.
- A `+ Rep` tap from the surface still increments the active set, and a delayed tap from a previous target set still emits `event=rejected` — the 08-01 and pre-existing behaviour must not regress.
- The diagnostics sheet shows the last rejected native action and its reason.
- Neither doc still claims the Flutter fallback always survives, nor that promotion is requested reflectively.
