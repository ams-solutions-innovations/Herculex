<objective>
Learn a per-user, per-exercise, per-device/placement profile from confirmed sets only, and let it suggest an RPE — but only when the profile has actually earned the right to, measured by cross-validated error rather than by row count alone.
</objective>

<read_first>

- `lib/features/reps/domain/rep_features.dart` (10-02) — the feature vector, its `v` version key, and which fields are nullable below 4 reps.
- `lib/features/reps/data/rep_tracking_repository.dart` (10-01) — `observationsFor({slug, source, placement, sensorType})` is the training query; the profile key is exactly that tuple.
- `10-CONTEXT.md` "RPE suggestion gating" — the model choice and the LOO gate are decided there, not here.
- `lib/features/workouts/domain/one_rep_max.dart` — the repo's idiom for a small pure estimator with a nullable return meaning "cannot estimate". Match it: a null return, not a sentinel value.

</read_first>

<tasks>

1. `rep_calibration.dart` — the profile, computed on demand from `RepSetObservations` rather than stored as a denormalised blob. Recomputing from ~30 rows is cheap and removes an entire class of staleness bug.

   `CalibrationProfile.fromObservations(List<RepSetObservationData>)` returns:
   - `sampleCount`, `distinctSessionCount`
   - median cadence and cadence spread (used to seed detector thresholds for this user)
   - the fitted RPE model, or null
   - `looMae`, or null
   - `CalibrationStatus`: `insufficient` | `countOnly` | `calibrated`

   The training set is filtered to observations whose feature `v` matches the current detector version. A detector change invalidates old vectors; training across versions silently corrupts the model. When filtering drops the count below the gate, status falls back to `insufficient` — which is correct and self-healing, not a bug.

   Only observations with a non-null `confirmedRpeX10` train the RPE model. A user who never enters RPE never gets an RPE suggestion, and that needs no special handling.

2. `rpe_estimator.dart` — ordinary least squares on standardised features, with:
   - Features: mean rep period, rep-period CV, normalised amplitude, final-rep period ratio, amplitude decay ratio. Rows with any null feature are excluded from the fit rather than imputed.
   - Leave-one-out cross-validation over the training rows, reporting MAE in RPE points.
   - Ridge regularisation with a small fixed lambda — at n≈10 with 5 correlated features, plain OLS will overfit and report a flatteringly low training error. Lambda is a constant, not a tuned hyperparameter; there is not enough data to tune one honestly.
   - `double? estimate(RepFeatures)` returning null when the gate fails.
   - Output clamped to 5.0–10.0 and rounded to the nearest 0.5, matching how `rpeX10` is entered elsewhere.

   **The gate** (all must hold): `sampleCount >= 10`, `distinctSessionCount >= 3`, `looMae <= 1.0`. Put it in one named predicate so it is testable and so a future change to the thresholds happens in exactly one place.

   The explicit non-goal: no term is hardcoded to assume a final-rep slowdown. The slowdown ratio is one input feature among five, and for a user whose RPE does not track it the fitted coefficient goes toward zero. If none of the features predict, `looMae` stays high and no suggestion is ever offered.

3. Invalidation — the profile key is (slug, source, placement, sensorType). A change to **any** component means a different profile, so a user who moves the phone from pocket to armband, or switches wrist to phone, starts at `insufficient` for that combination. Existing profiles are untouched, so switching back restores the old one. Surface this in the review sheet's "how this was measured" expander as "calibrating for this placement (4 of 10 sets)" — a stated progress state, not a silent downgrade.

4. Repository: add `Future<CalibrationProfile> profileFor({slug, source, placement, sensorType})` and a matching `calibrationProfileProvider` family. Cache per key within a session and invalidate on `recordObservation`.

5. Review sheet: consume the profile. When `calibrated`, pre-fill the RPE field with the estimate and label it as a suggestion. When `countOnly` or `insufficient`, leave the RPE field empty and show the progress state. The rep count field is unaffected by calibration status — counting does not depend on the RPE model.

6. `test/rep_calibration_test.dart`:
   - 9 sets → `insufficient`; 10 sets across 2 sessions → `insufficient` (the session gate bites independently of count).
   - 10 sets across 3 sessions with strongly RPE-correlated cadence → `calibrated`.
   - 10 sets across 3 sessions with **random** RPE → **not** `calibrated`. This is the anti-overfitting test and the direct check on the "don't assume slowdown" requirement.
   - A user whose RPE correlates with amplitude decay but *not* cadence still calibrates — the model must not be cadence-only.
   - Observations with an older feature `v` are excluded, and excluding them can push a profile back to `insufficient`.
   - Observations with null `confirmedRpeX10` are excluded from the RPE fit but still count toward cadence statistics.
   - A changed placement yields a fresh `insufficient` profile while the original key stays `calibrated`.

7. `test/rpe_estimator_test.dart`:
   - `estimate` returns null whenever the gate fails, for each of the three gate conditions independently.
   - Output is clamped to 5.0–10.0 and lands on a 0.5 boundary.
   - LOO MAE on a deterministic synthetic dataset matches a hand-computed expected value — the cross-validation must be verified, not trusted.
   - A feature vector with nulls (a set under 4 reps) returns null rather than throwing.

</tasks>

<success_criteria>

- No RPE is suggested below 10 confirmed sets, below 3 sessions, or above 1.0 LOO MAE — each condition independently sufficient to block.
- A synthetic user with random RPE never reaches `calibrated`.
- A synthetic user whose RPE tracks amplitude decay rather than cadence does reach `calibrated`.
- Changing placement or source produces a fresh profile without destroying the previous one.
- Feature vectors from an older detector version are never trained on.
- Rep counting is unaffected by calibration status.

</success_criteria>
