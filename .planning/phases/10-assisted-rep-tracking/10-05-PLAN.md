<objective>
Learn a per-user, per-exercise, per-device/placement profile from confirmed sets only, and let it suggest an RPE — but only when the profile has actually earned the right to, measured by cross-validated error rather than by row count alone.

Purpose: REP-05's real content is the *gate*, not the model. The LOO criterion is what makes "do not assume everyone slows down near failure" a checked property: for a user whose cadence carries no RPE signal the coefficients collapse toward zero, LOO error stays high, and the app simply never offers an RPE. That is the correct outcome and it needs no special-casing.
Output: `rep_calibration.dart`, `rpe_estimator.dart`, a repository `profileFor` query plus its provider family, review-sheet consumption, and tests that a random-RPE user never calibrates.
</objective>

  <action>
Create `lib/features/reps/domain/rpe_estimator.dart` fitting ordinary least squares on **standardised** features (subtract mean, divide by stddev per feature, computed from the training rows and stored on the model so `estimate` standardises identically).

Features, in this fixed order: `meanPeriodMs`, `periodCv`, `normalisedAmplitude`, `finalRepPeriodRatio`, `amplitudeDecayRatio`. **Rows with any null feature are excluded from the fit, never imputed** — a set under 4 reps contributes no training row rather than a fabricated one.

Apply **ridge regularisation with a small fixed lambda** (a named `const` in the file, not a parameter). At n around 10 with 5 correlated features, plain OLS overfits and reports a flatteringly low training error. Lambda is a constant, not a tuned hyperparameter — there is not enough data to tune one honestly, and a tuning loop would itself leak into the LOO estimate.

Implement leave-one-out cross-validation over the training rows: refit on n-1 rows and predict the held-out row, for each row; report MAE in RPE points (not in `rpeX10` units).

Expose the gate as **one named static predicate** `RpeEstimator.gatePasses({sampleCount, distinctSessionCount, looMae})` returning true only when `sampleCount >= 10 && distinctSessionCount >= 3 && looMae != null && looMae <= 1.0`. One predicate so it is directly testable and so a future threshold change happens in exactly one place.

`double? estimate(RepFeatures f)` returns null when the gate fails and null when `f` has any null feature. Clamp the output to 5.0-10.0 and round to the nearest 0.5, matching how `rpeX10` is entered elsewhere in the app.

**Explicit non-goal:** no term is hardcoded to assume a final-rep slowdown. `finalRepPeriodRatio` is one input feature among five; for a user whose RPE does not track it, the fitted coefficient goes toward zero on its own. The strings `slowdown` / `slow_down` may appear only as a feature or variable name, never in a branch condition.

Create `test/rpe_estimator_test.dart`: `gatePasses` is false for each of the three conditions failing independently while the other two pass; `estimate` returns null in each of those three cases; output is clamped to 5.0-10.0 and always lands on a 0.5 boundary; **LOO MAE on a deterministic synthetic dataset matches a hand-computed expected value** to within 1e-9 — the cross-validation must be verified, not trusted; a feature vector containing nulls returns null rather than throwing; a training set where every row has a null ratio feature yields a null `looMae` rather than an empty-matrix crash.
  </action>

  <action>
Create `lib/features/reps/domain/rep_calibration.dart` with `CalibrationProfile.fromObservations(List<RepSetObservationData>)`, **computed on demand rather than stored as a denormalised blob** — recomputing from around 30 rows is cheap and removes an entire class of staleness bug.

Returns `sampleCount`, `distinctSessionCount` (distinct `sessionId` values among surviving rows), `medianCadenceMs` and `cadenceSpread` (used to seed detector thresholds for this user), the fitted `RpeModel` or null, `looMae` or null, and a `CalibrationStatus` of `insufficient` | `countOnly` | `calibrated`.

**Version filter:** parse each row's `featuresJson` through `RepFeatures.fromJson` and **drop rows where it returns null** (a `v` mismatch). A detector change invalidates old vectors; training across versions silently corrupts the model. When filtering drops the count below the gate, status falls back to `insufficient` — that is correct and self-healing, not a bug, and must not be worked around.

**RPE training subset:** only rows with a non-null `confirmedRpeX10` train the RPE model. A user who never enters RPE never gets an RPE suggestion, and that needs no special handling. Those rows still count toward `medianCadenceMs` and `cadenceSpread`.

Status derivation: `calibrated` exactly when `RpeEstimator.gatePasses(...)` is true; `countOnly` when there are enough rows to compute cadence statistics but the gate fails; `insufficient` when there are too few surviving rows to compute anything. Do not add a fourth status and do not treat `countOnly` as an error.

**Invalidation by key:** the profile key is the four-part tuple (slug, source, placement, sensorType). A change to **any** component means a different profile, so a user who moves the phone from pocket to armband, or switches wrist to phone, starts at `insufficient` for that combination. Existing profiles are untouched, so switching back restores the old one. This falls out of `observationsFor`'s filter and requires no explicit invalidation logic.

Create `test/rep_calibration_test.dart`: 9 sets yields `insufficient`; 10 sets across 2 sessions yields `insufficient` (the session gate bites independently of count); 10 sets across 3 sessions with strongly RPE-correlated cadence yields `calibrated`; **10 sets across 3 sessions with random RPE yields NOT `calibrated`** — the anti-overfitting test and the direct check on the "don't assume slowdown" requirement; a user whose RPE correlates with `amplitudeDecayRatio` but *not* cadence still calibrates, proving the model is not cadence-only; observations with an older feature `v` are excluded and the exclusion can push a profile back to `insufficient`; observations with a null `confirmedRpeX10` are excluded from the RPE fit but still contribute to `medianCadenceMs`; a changed `placement` yields a fresh `insufficient` profile while the original key stays `calibrated`.
