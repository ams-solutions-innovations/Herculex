<tasks>

1. Add three tables to `lib/data/local/tables.dart`. None of them mixes in `SyncColumns` or `SyncTombstone`, and none is added to `syncedTableNames` — these are local-only by design (see 10-CONTEXT "Persistence and sync").

   **`RepTrackingSettings`** — one row, global consent and defaults.
   - `id` (int, autoIncrement)
   - `consentGrantedAt` (dateTime, nullable) — null means the consent screen has not been completed; this is the master gate
   - `consentVersion` (int, default 1) — bump forces re-consent if the data handling changes
   - `defaultSource` (text, nullable) — `wrist` | `phone`
   - `phonePlacement` (text, nullable) — `pocket_front` | `armband` | null; **must be non-null before the phone source is usable**
   - `hapticsEnabled` (bool, default true)

   **`RepTrackingExercisePrefs`** — per-exercise opt-in.
   - `id`, `exerciseSlug` (text), `enabled` (bool, default false), `preferredSource` (text, nullable), `updatedAt` (dateTime)
   - unique key on `{exerciseSlug}`
   - Keyed by slug, not `exerciseId`, so a catalogue re-import cannot orphan a preference.

   **`RepSetObservations`** — one row per *confirmed* set that had tracking active. This is the calibration training set (consumed by 10-05).
   - `id`, `exerciseSlug` (text), `sessionId` (int), `setEntryId` (int, nullable — nullable so a discarded set leaves no dangling FK; do not add a cascade reference, these rows must survive set deletion for calibration continuity)
   - `recordedAt` (dateTime)
   - `source` (text) — `wrist` | `phone`
   - `placement` (text, nullable)
   - `sensorType` (text) — `linear_acceleration` | `accelerometer`; profiles must not mix the two
   - `detectedReps` (int), `confirmedReps` (int), `confidence` (real, 0–1)
   - `suggestedRpeX10` (int, nullable), `confirmedRpeX10` (int, nullable)
   - `featuresJson` (text) — the derived feature vector; the schema for it is owned by 10-02
   - **No raw sample column.** Raw samples are never persisted.

2. Bump `schemaVersion` to 26 in `lib/data/local/database.dart`, register the three tables in the `@DriftDatabase` tables list, and add an `if (from < 26)` block to `onUpgrade` creating all three. Nothing else changes — no backfill is needed because absence of a row correctly means "no consent, not enabled".

4. Create `lib/features/reps/domain/rep_tracking_eligibility.dart` holding the closed slug list from 10-CONTEXT as a `const Set<String>`, plus:
   - `bool isEligible(String? slug)` — false for null, false for anything off the list
   - `RepMovement? movementFor(String slug)` — `RepMovement.pullUp` | `RepMovement.dip`, used by 10-02 to pick per-movement detector defaults and by 10-05 to keep profiles separate

   Comment each exclusion group with *why* (assisted variants change the acceleration profile; `negative-pull-up` and `scapular-pull-up` have no concentric cycle). A future contributor must not "helpfully" widen this list.

5. Create `lib/features/reps/data/rep_tracking_repository.dart` over `AppDatabase`:
   - `Future<RepTrackingSetting?> settings()`, `Future<void> grantConsent({required int version})`, `Future<void> revokeConsent()`
   - `revokeConsent()` clears `consentGrantedAt` **and deletes every `RepTrackingExercisePrefs` row and every `RepSetObservations` row** in one transaction. Revoking consent must leave no motion-derived data behind — that is the whole point of the control.
   - `Future<void> setExerciseEnabled(String slug, bool enabled)` — rejects ineligible slugs
   - `Future<bool> isEnabledFor(String slug)` — returns false when consent is null, regardless of the per-exercise row
   - `Future<void> recordObservation(...)`, `Future<List<RepSetObservationData>> observationsFor({required String slug, required String source, String? placement, required String sensorType})` — the filtered query 10-05 trains on

Create `lib/features/reps/presentation/rep_tracking_providers.dart`: `repTrackingRepositoryProvider`, a `repTrackingSettingsProvider` (`FutureProvider`), and `repTrackingEnabledForProvider` (`FutureProvider.family<bool, String>` over slug). Follow the provider idiom in `lib/features/analytics/presentation/analytics_providers.dart`.

7. Tests:

   - `test/schema_v26_test.dart` — v25 → v26 migration creates the three tables and preserves existing rows, following `test/schema_v24_test.dart`.
   - Repository tests over `AppDatabase.forTesting`: consent gates `isEnabledFor` even when a pref row says enabled; `setExerciseEnabled` rejects an ineligible slug; `revokeConsent` leaves zero rows in both `RepTrackingExercisePrefs` and `RepSetObservations`.
