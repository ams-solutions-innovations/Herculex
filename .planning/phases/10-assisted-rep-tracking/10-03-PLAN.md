<objective>
Get accelerometer samples from a wrist or a pocketed phone into the Dart detector from 10-02, with a provisional on-wrist counter for live feedback, buffered transport that survives disconnect, and no raw sample ever written to disk.
</objective>

<tasks>

1. Add three constants to **both** copies of `WearSyncPaths.kt`, keeping the files byte-identical:
   ```kotlin
   const val MESSAGE_REP_CAPTURE_START = "/herculex/reps/capture_start"
   const val MESSAGE_REP_SAMPLES = "/herculex/reps/samples"
   const val MESSAGE_REP_CAPTURE_END = "/herculex/reps/capture_end"
   ```
   The `/herculex` prefix is mandatory — the watch manifest's `MESSAGE_RECEIVED` intent-filter matches on it and anything outside is undeliverable with no error (LESSONS.md:85).

2. `ProvisionalRepCounter.kt` — the live on-wrist counter. Adaptive-threshold cycle counting, same shape as 10-02 but deliberately simpler: no calibration, no feature extraction, no confidence model. It exists solely to drive the live number and the haptic tick. Its output is **never sent to the phone as an authoritative count and never persisted.** Unit-test it in `android/wear/src/test/` for the clean-cycle and walking-noise cases so it does not buzz on a walk to the water fountain.

3. `RepCaptureController.kt` — sensor lifecycle and buffering:
   - Registers `TYPE_LINEAR_ACCELERATION` at `SENSOR_DELAY_GAME`; falls back to `TYPE_ACCELEROMETER` when absent and reports which it used in the start payload. No new manifest permission is required for either.
   - Maintains a 300-second ring buffer of raw samples in memory.
   - Batches ~1 s of samples per `MESSAGE_REP_SAMPLES` message. Each message carries `captureId`, a monotonic `seq`, `sensorType` and the sample array, so the phone can detect and report gaps rather than silently concatenating across a dropout.
   - On send failure, keeps the batch in the ring buffer and retries on the next connectivity callback. On `MESSAGE_REP_CAPTURE_END`, flushes everything still buffered.
   - Refuses to start below 15 % battery, returning a typed reason.
   - Hard-stops at 5 minutes, flushes, and reports `stoppedReason=cap`.
   - `stop()` unregisters the listener and clears the buffer. Wire it to service `onDestroy()` as well as normal set end.

4. Hook the controller into `WorkoutOngoingService`. Capture starts only on an explicit start command for a set — never on session start, never automatically. Expose the provisional count to `SetLoggerScreen` for display; label it provisional in the UI (10-04 owns the phone-side wording, the watch string lives here).

5. Phone side, `PhoneWearListenerService.kt`: route the three new paths through to Dart via the existing bridge. Follow the persistence lesson in LESSONS.md:72 — a batch that arrives while Flutter is not running must be held natively and delivered on attach, not dropped.

6. `lib/features/reps/data/rep_capture_service.dart`:
   - Registers `WearSyncService` callbacks for the three paths, mirroring `wear_workout_sync_service.dart:37-40`.
   - Accumulates batches by `captureId`, orders by `seq`, and records any gap as `missedBatches` — a gap must degrade confidence, not be papered over.
   - On capture end, resamples to 50 Hz and runs `RepDetector`, producing a `RepSuggestion`.
   - Holds raw samples in a private in-memory buffer keyed by `captureId` and **clears it as soon as detection completes**. No file, no database, no log line containing sample values.
   - Exposes a `TrackerState` stream (the enum from 10-CONTEXT) and emits `manual` with a stated reason on disconnect, battery refusal, or an empty sample set.

7. `lib/features/reps/data/phone_motion_source.dart`: add `sensors_plus` to `pubspec.yaml` and implement the phone-local source with the identical `MotionTrace` output. **It refuses to start unless `RepTrackingSettings.phonePlacement` is non-null** — placement must be explicitly chosen, not defaulted (REP-02). Same 5-minute cap and battery gate.

8. `test/rep_capture_service_test.dart` — against a fake bridge, no device:
   - In-order batches reconstruct the original trace exactly.
   - A dropped `seq` sets `missedBatches` and lowers reported confidence.
   - Capture end with zero batches yields `TrackerState.manual` with a reason, never a zero-rep suggestion. "Zero reps detected" and "nothing was captured" must never be conflated.
   - The raw buffer is empty after detection completes — assert on the service's own accessor, so the discard is a tested property rather than a comment.
   - Starting the phone source with a null placement throws / returns a refusal.

</tasks>
