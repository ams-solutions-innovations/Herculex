<objective>
Build the client transport: a gateway over the three RPCs and the backlog query, a channel service
owning the private broadcast subscription and presence, and a pure ordering machine that turns
unordered arrivals into a strictly-increasing, deduped, gapless event stream.

Purpose: BUD-04. The durable log is only useful if the client consumes it correctly — the naive
"fetch backlog then subscribe" order loses every event committed in the gap. BUD-06's client half also
lands here: the explicit `session_ended` teardown, because Realtime authorisation is cached for the
connection's lifetime and a policy revocation does not evict a live subscriber.

Output: three files under `lib/features/buddy/data/`, all inside the scope-boundary gate, plus a fake
gateway and an ordering test suite.
</objective>

    - Starting with `lastSeenSeq: 0` and a gateway holding events 1..5, `start()` applies exactly 1,2,3,4,5 in that order and `lastAppliedSeq` is 5
    - An event enqueued *before* `start()` completes is buffered, then dropped during drain if its seq is `<=` the highest backfilled seq, and applied if it is higher — the gap-between-subscribe-and-query case, which is the whole reason subscribe precedes backfill
    - `onLiveEvent` with `seq == lastAppliedSeq + 1` applies immediately without touching the gateway
    - `onLiveEvent` with `seq <= lastAppliedSeq` is dropped and `apply` is not called (the broadcast echo of the client's own append)
    - `onLiveEvent` with `seq > lastAppliedSeq + 1` calls `fetchEventsSince(afterSeq: lastAppliedSeq)` exactly once and applies the returned run in order, rather than applying the out-of-order event
    - `commitSeq` is called only *after* the corresponding `apply` future completes, so a throw from `apply` leaves `lastSeenSeq` unadvanced and the event replays on the next start
    - Replaying `start()` against the same gateway with the already-advanced `lastSeenSeq` applies nothing
    - Two `onLiveEvent` calls arriving out of order (5 then 4, from a lastApplied of 3) end with `lastAppliedSeq == 5` and `apply` called for 4 before 5
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Realtime broadcast → client apply path | Payloads arriving over the socket are server-originated but unordered and possibly duplicated |
| server error text → user-facing UI | A distinguishable join failure is an existence oracle |
| buddy channel lifecycle → auth/sync lifecycle | Coupling them lets an unrelated event kill a live session |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-03 | Tampering | forged or replayed event applied out of order | high | mitigate | `BuddyEventStream` applies strictly in `seq` order, dedupes at or below `lastAppliedSeq`, and refetches the backlog on any gap; `seq` itself is server-assigned and clients cannot insert into the log |
| T-11-02 | Information disclosure | join failure cause leaked to the client | high | mitigate | `SupabaseBuddyGateway.joinSession` converts every `PostgrestException` to a fieldless `BuddyJoinRejected`, carrying no server message |
| T-11-06 | Information disclosure | stale subscriber still receiving after the session ends | medium | mitigate | Explicit `sessionEnded` handling drives `removeChannel` client-side rather than relying on a policy cache that is never re-queried |
| T-11-19 | Denial of service | buddy channel torn down by an unrelated lifecycle | medium | mitigate | `BuddyChannelService` owns its own channel; nothing is added to `SupabaseSyncBackendService`, whose `dispose()`/`onCancel` iterate `_channels` wholesale |
| T-11-20 | Spoofing | private channel subscribed with the anon key during the cold-start race | medium | mitigate | `connect()` asserts `client.auth.currentSession != null` and throws a named `StateError`; the provider layer gates on `authSessionProvider`, mirroring `syncServiceProvider` |
| T-11-13 | Information disclosure | scope leaking into the transport module | high | mitigate | All three new files live under `lib/features/buddy/data/` and are covered by `test/buddy/buddy_scope_boundary_test.dart`, re-run as a gate in every task here |
