<objective>
Make program generation honor the user's time budget for real (D-05, D-06, D-07, PRES-02): compute an itemized per-day duration estimate via `WorkoutDurationEstimator` after all of a day's slots are planned, and if it exceeds `workoutDurationMinutes * 1.10`, trim accessory/isolation slots (reduce set counts, then drop entirely) — never `SlotRole.main`/`supplemental` — until the day fits or no more accessory/isolation slots remain. The per-slot estimate feeding this trim decision must itemize real warmup ramps (via `WarmupResolver`, D-06) and real unilateral doubling (from the exercise catalog), not empty/false placeholders — otherwise the trim pass systematically under-estimates every day with main-lift warmups or unilateral accessory work, and the materialized session can blow past `workoutDurationMinutes` despite "passing" the trim check.

Also switch the stored-override write path from the ad-hoc `templateSets` JSON blob to `SlotPrescriptionCodec.encode` (D-01, PRES-01), and persist `SmartProgramConfiguration.allowTimeSavingSetTechniques` onto the generated `Programs` row (PRES-04) so 18-03's live-workout gate and 18-04's resolver have a durable value to read after generation finishes.

Purpose: Close the loop between the user's declared time budget and what actually gets generated; make the opt-in durable past generation time.
Output: Updated `smart_program_planner.dart` with a two-pass per-day trim loop fed by real warmup/unilateral inputs, codec-based writes, persisted opt-in.
</objective>

Note on `targetPercentOf1Rm`: this planner tracks prescriptions as RIR-based (`_Target.rir`), not `%1RM` — there is no existing `%1RM` field on `_Target`. Per D-08, `WarmupResolver.resolve` treats `targetPercentOf1Rm: null` as the moderate/no-percent case, which is the correct input for every RIR-based slot here. The one exception is `SlotTrainingMethod.maxEffort` (already special-cased to `_Target(1, 1, 3, 1, 300)` at `_targetFor`), which 18-04's resolver always treats as near-max (`targetPercentOf1Rm: 0.90`) — mirror that same constant here so the trim-time estimate and the materialize-time resolve agree.

Note on unilateral detection: there is no boolean "unilateral" column on `ExerciseCatalog`. The only existing signal is `ExerciseCatalogData.movementPatternRaw`, which the seed data (`assets/data/exercises.json`) annotates with the literal substring `"unilateral"` for single-limb movements (e.g. `"Elbow Flexion (unilateral)"`). Treat `(exercise.movementPatternRaw ?? '').toLowerCase().contains('unilateral')` as the unilateral flag — this is the same metadata 18-04 or any later plan would use if it needed the same signal; do not add a new column for this.
