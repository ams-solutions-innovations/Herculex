## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| DB row -> codec decode | `prescriptionCodecJson` is user-database-resident text that a future corrupted row, manual DB edit, or partial write could make malformed. |
| Local schema -> Supabase schema | The additive migration must keep both sides in lockstep or `SyncService`'s `SELECT *` forward breaks (PGRST204) and rows quarantine after 8 attempts. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-------------------|
| T-18-01 | Tampering | `SlotPrescriptionCodec.decode` | mitigate | `try/catch` around `jsonDecode` + field access returns `null` on any malformed/adversarial input rather than throwing or returning a partially-populated object; hard version gate (`codecVersion != wireVersion` -> `null`) rejects any future/incompatible shape instead of guessing. |
| T-18-02 | Information Disclosure | `prescriptionCodecJson` column | accept | Prescription data (sets/reps/%1RM) is training content, not sensitive PII; existing RLS on `program_day_exercises` (owner-only) already covers it, unchanged by this migration. |
| T-18-03 | Denial of Service | `onUpgrade` addColumn guard | mitigate | `addIfMissing` checks `pragma_table_info` before altering, so migration fixtures at any completeness level (per CLAUDE.md's documented narrow/complete fixture split) do not fail the upgrade path. |
| T-18-SC | Tampering | `dart run drift_dev` (dev-time only, no new package installs) | accept | No new npm/pip/cargo dependency introduced by this plan; `drift_dev` is an existing dev_dependency already vetted in prior phases. |

</threat_model>
