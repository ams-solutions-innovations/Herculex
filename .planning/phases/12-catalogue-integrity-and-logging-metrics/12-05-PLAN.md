<objective>
Close EXR-05: make the set row ask for, store and show the units its exercise is actually
measured in, and keep those sets out of the aggregates that assume kilograms x reps.

12-03 built the `LoggingMetric` registry and 12-04 gave `set_entries` the three nullable
columns (`durationSeconds`, `distanceM`, `calories`, Drift v31 / Supabase 0013). Nothing
reads either yet: `active_exercise_card.dart` still renders a fixed weight/reps/RPE row for
every exercise, and `workouts_repository.updateSet` has no parameter that could reach the
new columns. A Plank still records kilos x reps.

Output: the logger branches on `metric.fields`; the repository carries all five fields;
tonnage, session reps and 1RM exclude non-rep work by metric; history renders each set in
its own units.
</objective>

<tasks>

## Task 1 - Display and input for the three new units (`lib/core/units.dart`)

`WeightFormat` is the existing boundary between stored metric values and the user's chosen
system. Distance needs the same treatment; duration and calories do not (seconds and
kilocalories are system-independent).

- Add `DistanceFormat`, bound to the same `unitsProvider`, with `toDisplay`/`toM`/`suffix`
  (`m` / `yd`) and a `format` that promotes to `km` / `mi` above one whole unit.
  Storage stays metres, exactly as weight storage stays kilograms.
- Expose `distanceFormatProvider`.

Do **not** add a separate unit preference. One `MeasurementUnit` governs the whole app.

## Task 2 - `set_metric_format.dart`

A new domain file so the same parse/format rules serve the logger, history and any later
surface:

- `formatDuration(int seconds)` produces `45s`, `1:30`, `12:05`, `1:02:30`.
  `parseDuration(String)` accepts both a bare seconds count and `m:ss` / `h:mm:ss`.
- `formatCalories`, and thin wrappers over `DistanceFormat`.
- `summariseSet(SetEntryData, {LoggingMetric, WeightFormat, DistanceFormat})` produces the
  single one-line rendering of a set (`60 kg x 8`, `2:00`, `40 kg - 20 m`, `250 kcal`),
  replacing the four hardcoded weight-times-reps strings.

`summariseSet` must read only the fields the metric declares, so a `weight_reps` set is
byte-identical to the string the app renders today.

## Task 3 - Repository (`workouts_repository.dart`)

- `addSet` gains `int? durationSeconds`, `double? distanceM`, `int? calories`.
- `updateSet` gains the same three plus `clearDurationSeconds` / `clearDistanceM` /
  `clearCalories`, following the exact `bodyweightKg`/`chainsKg` absent-vs-null idiom
  already in the method. Null-with-no-clear means "leave alone"; the clear flag writes SQL
  NULL. This distinction is what 0013 is nullable for.

## Task 4 - Metric-driven set row (`active_exercise_card.dart`)

- `_HeaderRow` takes the `LoggingMetric` and labels its columns from `metric.fields`
  (`KG`/`LB`, `REPS`, `TIME`, `M`/`YD`, `KCAL`) plus the unchanged `RPE`.
- `_SetRow` takes the metric, owns one `TextEditingController` per declared field, and
  renders them in `metric.fields` order. `_commit` writes only the declared fields and
  passes `null` for the rest.
- The weight long-press plate calculator stays attached to the weight field only; the
  rep-tracker prefill path (`prefillReps`) applies only when the metric is rep-based.
- The "copy the previous set's value on completion" convenience generalises to every
  declared field.
- New sets seeded from the previous set copy the declared fields too.

Non-rep sets still write `weightKg: 0` / `reps: 0` - those columns are NOT NULL and Task 5
is what keeps the zeros out of the aggregates.

## Task 5 - Aggregation exclusion

- `ResolvedSet` exposes `metric` and returns `0` from `tonnageKg` when `!metric.isRepBased`.
  Gate on `isRepBased`, not on `isLoaded`: a bodyweight pull-up is rep work whose effective
  load is the athlete's own mass and must keep counting.
- `SessionSummary.from` adds `rs.set.reps` only for rep-based metrics.
- `AnalyticsRepository.weeklyTonnage` joins `exerciseCatalog` and skips non-rep-based rows.
- `AnalyticsRepository.topOneRms` skips exercises whose metric is not both rep-based and
  loaded - a 1RM of a Plank is not a number.

## Task 6 - Display sites

Replace the hardcoded weight-times-reps strings in `active_exercise_card.dart` (last/next
hint and micro-label), `workout_history_view.dart` and `dynamic_workout_view.dart` with
`summariseSet`. `exercise_details_view.dart`'s PR card is rep-based by construction and
stays as is.

## Task 7 - Tests

`test/logging_metric_ui_test.dart`:
- A `time` exercise renders one duration field and no weight/reps field.
- A `weight_distance` exercise renders weight and distance.
- A `weight_reps` exercise renders the pre-existing three-field row (regression).
- Typing `2:00` into a Plank's duration field and completing the set stores
  `durationSeconds = 120` and leaves `distanceM`/`calories` null.

`test/set_metric_tonnage_test.dart`:
- A 40 kg x 20 m sled push contributes 0 tonnage and 0 reps.
- A 100 kg x 5 squat in the same session contributes 500 kg - the exclusion is per set.
- A bodyweight pull-up still contributes its bodyweight tonnage.
- `topOneRms` returns no entry for a duration-only exercise.
