<objective>
Close VERIFICATION.md gap #1 for Phase 21: `CrossfitScalingPolicy.complexityCheck` (lib/features/programs/domain/crossfit_scaling_policy.dart:144) is fully implemented and unit-tested but has zero production call sites. `CrossfitProgramPlanner.segmentNeedsFor` generates metcon needs before exercise identities are known, so there is currently no seam where the "never stack 2+ advanced/just-unlocked movements in one metcon" hard rule can fire.

The real seam is `SmartProgramPlanner._createStableSlots` in `lib/features/programs/data/smart_program_planner.dart` — it resolves one `_SlotNeed` at a time, in order, for every slot on a CrossFit day (including all of that day's metcon slots), and it is the only place that has both the metcon's `metconGroupKey` grouping AND each slot's own ranked candidate pool of concrete `ExerciseCatalogData` rows.

Purpose: Make the documented D-06 hard safety rule ("stacking two or more advanced/just-unlocked movements in one metcon is never allowed, regardless of level") actually enforced at generation time, with a real candidate-pool substitution — not a passive/logged-only check — and an explicit, non-silent rationale when substitution is impossible.

Output: `_createStableSlots` calls `CrossfitScalingPolicy.complexityCheck` once per metcon slot it resolves, filters that slot's own candidate pool to avoid a second advanced/just-unlocked pick when one is already committed for the same `metconGroupKey`, and records `complexityCheck`'s rationale into the slot's `why` (which flows into `ProgramDayExercises.prescriptionWhy`) whenever the check is unsafe. Two new regression tests in `smart_program_planner_test.dart` prove both branches fire.
</objective>
